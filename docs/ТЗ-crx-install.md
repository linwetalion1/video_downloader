# ТЗ: Упаковка и установка .crx для Edge-расширения (sideload)

## 1. Контекст

Готовое расширение для Microsoft Edge (Manifest V3): поиск, предпросмотр, фильтрация и массовое скачивание изображений с веб-страниц. Проект `image_downloader_explorer`, стек: TypeScript + React + Vite, сборка в `dist/` командой `npm run build`. Код, тесты (51), README — всё на месте и работает.

## 2. Задача

Дать пользователю **однофайловую установку** расширения на его машине без магазина: упакованный `.crx`, который можно перетащить на `edge://extensions` и включить. При невозможности собрать `.crx` — гарантированный fallback.

## 3. Текущее решение (уже реализовано)

- `scripts/package.mjs` (`npm run package`):
  1. `npm run build`;
  2. инжектит в `dist/manifest.json` поле `"key"` = base64(DER SPKI) ключа разработчика `keys/edge-key.pem` (создаётся один раз командой `generateKeyPairSync("rsa", 2048, pkcs8)` — стабильный ID между пересборками);
  3. пакует `.crx` **только официальным паковщиком Edge**: `msedge.exe --pack-extension=...\dist --pack-extension-key=...\keys\edge-key.pem`, обязательно с отдельным `--user-data-dir` (иначе флаг игнорируется запущенным браузером); ждёт появления `dist.crx`, копирует `dist.pem` в `keys/`;
  4. параллельно собирает `release/...zip` через `fflate`;
  5. выход: `release/image-downloader-explorer.crx` + `.zip`.
- Инструкция в README, раздел «Загрузка расширения в Edge».

## 4. Грабли (НЕ повторять)

1. **Рукописный CRX3 нельзя**. Пробовали: самодельный CRX3 с CBOR-заголовком и подписью RSA-SHA256 по zip → Edge отвечает `CRX_HEADER_INVALID`. Современный Edge использует **protobuf**-заголовок `CrxFileHeader` (поле `sha256_with_rsa`=2, `crx_verifier`, плюс собственное поле 16 с внутренними данными) и иную схему подписи (проверка подписи по zip не проходит ни для одного известного контекста). Вывод: CRX пишет только сам браузер через `--pack-extension`.
2. **Установка .crx при выключенном «Режиме разработчика»** блокируется: Edge пишет «This extension is not from any known source…», тумблер включения неактивен.
3. **Старая версия без `"key"` в манифесте** Edge не «узнаёт» — нужен ключ в manifest, чтобы расширение считалось «известным источником».

## 5. Ожидаемый сценарий у пользователя

1. `edge://extensions`
2. Удалить старую версию (ID изменился);
3. Включить «Режим разработчика»;
4. Перетащить новый `.crx` в окно браузера → установить → включить.

Fallback: распаковать `.zip` → «Загрузить распакованное» (этот путь не проверяется по источнику и работает всегда, подписи не требует).

## 6. Открытые вопросы / кандидаты на следующий шаг

- Проверить чистую установку нового `.crx` (dev-mode вкл., без следов старой версии) — переключатель должен быть активен.
- Край: на таких страницах как `edge://extensions` может быть пометка «Управляется вашей организацией» — тогда sideloading запрещён политиками (`ExtensionInstallBlocklist`/`ExtensionSettings`) и решается только администратором. Оценить, нужен ли enterprise-путь (реестр `ExtensionInstallForcelist` = `ID;file:///путь/файл.crx`).
- Убедиться, что `--pack-extension-key` даёт стабильный ID при повторном `npm run package` (должен не меняться).
- Опционально: удобный `install.cmd`, который открывает `edge://extensions` и кладёт путь к `.crx` в буфер обмена.

## 7. Критерии приёмки

- `npm run package` на машине с Edge/Windows создаёт `.crx`, который:
  - ставится перетаскиванием при включённом «Режиме разработчика»;
  - включается без предупреждения «not from any known source»;
  - имеет стабильный ID при повторной упаковке;
  - side panel открывается по клику на иконку, расширение работает.
- Без найденного `msedge.exe` скрипт не падает в непонятную ошибку: выдаёт `.zip` + понятную инструкцию «Загрузить распакованное».
